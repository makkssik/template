# TripGo — сервис поездок

Сервис создаёт и завершает поездки. В ЛР3 добавлены запись координат через
`POST /api/v1/trips/{tripId}/positions` и чтение маршрута через
`GET /api/v1/trips/{tripId}/positions`. Если от водителя давно нет координат,
сервис запрашивает новую через Push Service. [HTTP-контракт](contracts/openapi/trip-service.openapi.yaml)

## Запуск из клона

Нужны Go 1.26.2, Docker и [tripgoctl](https://github.com/course-go-autumn-2026/course-infra).
В корне репозитория выполните:

```sh
tripgoctl cluster start       # один раз на машине
tripgoctl environment start
tripgoctl connect             # адреса сервисов, Grafana и Jaeger
make migrate
make run
```

`tripgoctl environment start` поднимает PostgreSQL, Push Service и окружение
телеметрии, затем записывает адреса в `.env`. `make run` загружает
[config/service.env](config/service.env), затем `.env`. Значения из `.env` имеют приоритет.
После запуска `GET /health` возвращает `200`, а `GET /ready` проверяет соединение
с PostgreSQL и возвращает `200` или `503`.

## Архитектура

`cmd/trip-service` запускает сервис. В `internal/container` вручную собираются
обработчики, сценарии, репозитории, гейтвей Push Service и фоновые компоненты.

- HTTP-обработчики разбирают и проверяют запросы, вызывают usecase и переводят доменные ошибки в HTTP-ответы.
- Usecase задаёт границы транзакций и вызывает методы домена и репозиториев. Доменные модели поездки и позиции хранятся в `internal/domain` рядом со своими правилами.
- Репозитории выполняют SQL. Менеджер транзакций и выбор исполнителя запроса находятся вместе в `internal/infra/postgres`, поскольку используют один ключ транзакции в контексте.
- Узкие интерфейсы объявлены в `contract.go` у потребителя. Например, воркер определяет, какие операции ему нужны от репозитория и Push Service. Контейнер передаёт реализации, в тестах их заменяют моки.

## Решения

- **Транзакции.** `TxManager.Do` передаёт транзакцию через контекст. Репозитории используют её для всех запросов внутри `Do`, вложенный вызов переиспользует ту же транзакцию. При успехе менеджер делает commit, при ошибке или панике — rollback с пробросом ошибки или паники. Изменение статуса поездки и запись в историю атомарны.
- **Конкурентные запросы.** Достаточно `READ COMMITTED`: частичный уникальный индекс по водителю запрещает две активные поездки даже при одновременном создании. При завершении `SELECT … FOR UPDATE` блокирует поездку до конца транзакции. Второй запрос увидит статус `completed` и получит `409`.
- **Координаты.** Добавление точки блокирует ту же строку поездки, проверяет статус, сохраняет точку и обновляет `last_position_at` в одной транзакции. Благодаря `GREATEST` поздно доставленная точка попадает в маршрут, сохраняя время самой свежей координаты. Маршрут отсортирован по `recorded_at`, при равенстве — по `id`.

## Опрос устаревших поездок

```text
Сканер по таймеру → приоритетная очередь → пул воркеров → Push Service (HTTP)
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSITION_CHECK_INTERVAL` | `30s` | Период сканирования и повторной постановки |
| `POSITION_STALE_AFTER` | `60s` | Порог устаревания с момента последней координаты или начала поездки |
| `POSITION_WORKERS` | `4` | Число постоянных воркеров |
| `POSITION_QUEUE_SIZE` | `100` | Максимум ожидающих задач, без выполняющихся |
| `POSITION_SCAN_BATCH_SIZE` | `100` | Размер SQL-батча, бонусное задание |
| `PUSH_HTTP_URL` | из `.env` от tripgoctl | Адрес Push Service |
| `PUSH_REQUEST_TIMEOUT` | `1s` | Общий таймаут проверки актуальности и отправки задачи |
| `PUSH_KEEP_ALIVE` | `30s` | Интервал TCP keep-alive для соединений с Push Service |
| `PUSH_IDLE_CONN_TIMEOUT` | `90s` | Время хранения простаивающего HTTP-соединения с Push Service |

На каждом тике сканер выбирает из БД активные поездки, у которых с момента
последней координаты (или начала поездки, если координат ещё нет) прошло больше
`POSITION_STALE_AFTER`. Сначала идут поездки, которые молчат дольше всех.
Следующая порция начинается после пары `(COALESCE(last_position_at, started_at), id)`
из последней строки предыдущей. Этому порядку соответствует частичный индекс
`trips_active_position_idx` по активным поездкам.

**Когда очередь заполнена**, более старая поездка вытесняет самую свежую из
ожидающих. Иначе сканер отклоняет новую задачу. В обоих случаях он записывает
`Warn`, увеличивает `tripgo.stale_checks{result="dropped"}` и заканчивает текущий
обход. На следующем тике сканер снова начинает с самых старых поездок.
Пока задача ожидает или выполняется, повторно в очередь она не попадает.

Воркер забирает самую старую задачу, проверяет в БД, что поездка всё ещё
активна и координата не обновилась, затем отправляет один HTTP-запрос.
После успешного сохранения новой координаты сервис удаляет ожидающую задачу
или отменяет контекст выполняющейся. При остановке сервис завершает текущие
HTTP-запросы, останавливает сканер и даёт воркерам разобрать очередь в пределах
общего `SHUTDOWN_TIMEOUT`.

## Проверка

| Команда | Что проверяет или делает |
|---|---|
| `make generate` | Генерирует код по OpenAPI и моки |
| `make build` | Собирает все пакеты |
| `make lint` | Запускает golangci-lint. Для первой установки нужен `curl` |
| `make test` | Запускает unit-тесты без БД с `-race -count=2` и выводит покрытие domain + usecase |
| `make test-integration` | Запускает интеграционные тесты PostgreSQL с `-race -count=2` |

Интеграционные тесты используют `TEST_DATABASE_URL` или `DATABASE_URL` из `.env`.
Каждый тест создаёт и удаляет собственную схему. Пользователю БД нужно право
`CREATE SCHEMA`.

Для сдачи ЛР3 приложите к описанию PR скриншот метрик пула под нагрузкой и план
выборки **второй порции**. В Grafana импортируйте [дашборд пула](config/grafana-positions.json)
с источником `prometheus`. План можно получить тестом на 10 000 поездках:

```sh
. ./.env
TEST_DATABASE_URL="${TEST_DATABASE_URL:-$DATABASE_URL}" go test -tags=integration -run '^TestStaleIndexPlan$' -count=1 -v ./internal/repository/trip
```
