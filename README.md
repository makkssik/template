# TripGo — лабораторная работа 2

HTTP API поездок на `net/http` и `chi`, PostgreSQL через `pgxpool`, SQL через
`squirrel`. Создание и завершение поездки записывают историю статуса в одной
транзакции с изменением поездки.

## Требования

- Go 1.26.2 (версия указана в `go.mod`).
- Docker и установленный `tripgoctl` из
  [course-infra](https://github.com/course-go-autumn-2026/course-infra).
- `golangci-lint` v2 (проверено на 2.11.4).
- Для примеров запросов — `curl`, для извлечения ID — `jq`.

Версии `goose`, `mockgen` и `oapi-codegen` закреплены в `go.mod`; инструменты запускаются
через `go tool`.

## Запуск из клона

В корне репозитория:

```sh
go mod download
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

Кластер создаётся один раз. `environment.toml` выбирает окружение ЛР2 с PostgreSQL и observability.
`tripgoctl environment start` создаёт `.env` с адресами БД и OTLP-коллектора.
Дополнительные HTTP-таймауты сервиса хранятся в `config/service.env`, который
входит в репозиторий. Вручную дополнять сгенерированный `.env` для запуска не нужно.
`.env.example` служит справочным примером и при запуске не загружается.

```sh
make generate
make build
make migrate-up
make migrate-status
make run
```

`make run` сначала экспортирует настройки из `config/service.env`, затем из `.env`.
Значения из `.env` имеют приоритет; адреса БД и коллектора берутся только оттуда.
Повторный `tripgoctl environment start` не затрагивает `config/service.env`.
На старте проверяется конфигурация
и выполняется `Ping` PostgreSQL. При ошибке сервис завершается с сообщением.
`Ctrl+C` запускает graceful shutdown; поддерживается и `SIGTERM`.

## Переменные окружения

Все параметры HTTP и БД, `LOG_LEVEL`, `SHUTDOWN_TIMEOUT`, имя сервиса, OTLP-адрес, протокол и sampler обязательны. Таймауты и время жизни соединений должны быть
положительными; длительности задаются в формате Go, например `3s` или `30m`.
Конфигурация читается из env через `cleanenv`; ограничения значений заданы
тегами `validator`. Уровень логирования принимается без учёта регистра.

| Переменная | Значение в примере | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | `10s` | Чтение запроса |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Чтение заголовков |
| `HTTP_WRITE_TIMEOUT` | `10s` | Запись ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Ожидание следующего запроса |
| `LOG_LEVEL` | `info` | Уровень JSON-логов `slog` |
| `SHUTDOWN_TIMEOUT` | `10s` | Общий бюджет остановки HTTP, OTel SDK и пула |
| `DATABASE_URL` | из `.env`, созданного `tripgoctl` | Подключение к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | Максимум соединений, больше нуля |
| `DATABASE_MIN_CONNS` | `2` | Минимум соединений, от нуля до максимума |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | Время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | Подключение к БД |
| `DATABASE_QUERY_TIMEOUT` | `3s` | Запрос к БД и проверки доступности |
| `OTEL_SERVICE_NAME` | `trip-service` | Имя сервиса в телеметрии |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | из `.env` | Коллектор телеметрии |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` | `http/protobuf` или `grpc`; порт должен соответствовать протоколу |
| `OTEL_RESOURCE_ATTRIBUTES` | `service.namespace=tripgo,deployment.environment=local,service.version=dev` | Атрибуты ресурса; для сборки укажите её версию вместо `dev` |
| `OTEL_TRACES_SAMPLER` | `parentbased_always_on` | Семплирование, читается OTel SDK |

Для ratio-семплера SDK принимает `OTEL_TRACES_SAMPLER_ARG` от 0 до 1.
Версия сервиса по умолчанию — `dev`; остальные атрибуты ресурса приходят из env.
При проверке можно задать `OTEL_METRIC_EXPORT_INTERVAL=2000` (миллисекунды),
чтобы быстрее увидеть метрики; стандартный интервал SDK — 60 секунд.


`.env` и `.tripgo/` исключены из git. Адреса и учётные данные БД в коде отсутствуют.

## HTTP API

| Метод | Путь | Результат |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, поездка и заголовок `Location` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, поездка |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, завершённая поездка; тело запроса пустое |
| `GET` | `/health` | `200`, процесс работает; обращений к БД нет |
| `GET` | `/ready` | `200` при доступной БД, иначе `503` |

Успешные ответы и обе служебные ручки возвращают `application/json`.
Ошибки бизнес-ручек — `application/problem+json` с полями `type`, `title`,
`status`, `detail`, `instance`, `code`:

- `400 invalid_request` — неверный JSON, UUID, отсутствующие или неизвестные
  поля, `null`, недопустимые координаты или отрицательная цена;
- `404 trip_not_found` — поездки нет;
- `409 driver_busy` — у водителя уже есть активная поездка;
- `409 trip_completed` — повторное завершение;
- `500 internal_error` — внутренняя ошибка, подробности доступны в логе.

### Пример запросов

В другом терминале загрузите `.env` и выберите адрес HTTP-сервера:

```sh
. ./.env
case "$HTTP_ADDR" in
  :*) BASE_URL="http://localhost$HTTP_ADDR" ;;
  *) BASE_URL="http://$HTTP_ADDR" ;;
esac

curl -i "$BASE_URL/health"
curl -i "$BASE_URL/ready"

TRIP_ID=$(curl -fsS -X POST "$BASE_URL/api/v1/trips" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"5cb72c04-7650-45c9-a79b-bcdba0631e0c",
       "driver_id":"8860b315-ec86-42eb-a17c-7c163d721ff5",
       "start_point":{"latitude":59.9398,"longitude":30.3146},
       "end_point":{"latitude":59.9290,"longitude":30.3626},
       "price":1450}' | jq -r '.id')

curl -i "$BASE_URL/api/v1/trips/$TRIP_ID"
curl -i -X POST "$BASE_URL/api/v1/trips/$TRIP_ID/finish"
curl -i -X POST "$BASE_URL/api/v1/trips/$TRIP_ID/finish"
```

Последний запрос возвращает `409 trip_completed`. Повторное создание на того же
водителя до завершения первой поездки возвращает `409 driver_busy`.

## Команды и проверка

```sh
make build                          # go build ./...
make test                           # -race -count=2, итоговое покрытие domain + usecase
make test-integration               # PostgreSQL, -race -count=2, изолированные схемы
make lint                           # обязательные линтеры + depguard
make fmt                            # gofumpt + gci
make generate                       # OpenAPI + gomock через go:generate
make migrate                        # то же, что migrate-up
make migrate-up
make migrate-status
make migration-create NAME=change   # новая последовательная SQL-миграция
make connect
```

`make migrate-down` откатывает одну миграцию. На отдельной тестовой БД можно
проверить полный цикл: два вызова `make migrate-down`, затем `make migrate-up`.
Откат удаляет таблицы с данными. Применённые миграции не редактируются.

Для проверки `/ready` оставьте сервис запущенным: после `tripgoctl environment
stop` ожидается `503`, после `tripgoctl environment start` и восстановления
подключения — `200`. `/health` продолжает отвечать `200`.

Проверьте также 20 параллельных созданий на одного свободного водителя: ожидается
один `201` и 19 ответов `409 driver_busy`. Для 20 параллельных завершений одной
активной поездки ожидается один `200` и 19 ответов `409 trip_completed`.
В истории этой поездки должны остаться ровно две записи: создание и завершение.

`make test` не требует БД. В тестах usecase мокаются репозитории, менеджер
транзакций и наблюдатель бизнес-событий; в тестах HTTP — usecase. Отдельно
проверяются доменные переходы, валидация, маппинг ошибок, middleware и паника.
Тесты телеметрии проверяют корреляцию логов, а через локальный HTTP-сервер —
OTLP-экспорт трейса и счётчика при остановке SDK и атрибуты ресурса.
Суммарное покрытие домена и usecase должно быть не ниже 50%.

`make test-integration` читает `TEST_DATABASE_URL`, а если он не задан —
`DATABASE_URL` из `.env`. Пользователю БД нужно право `CREATE SCHEMA`.
Каждый тест создаёт уникальную схему, применяет в ней существующие миграции
и удаляет только эту схему после теста. Проверяются rollback при ошибке и
панике, вложенный `Do`, конкурентное создание и завершение. Рабочие таблицы
окружения тесты не очищают. Повторный запуск входит в команду.

Если локально установлено несколько версий Go и coverage сообщает
`compile: version ... does not match go tool version ...`, запускайте
`GOTOOLCHAIN=go1.26.2 make test`, чтобы дочерние инструменты использовали ту же
версию, что и компилятор.

## Архитектура

```text
HTTP handler → usecase → domain
                  ↓ интерфейсы потребителя
              repository → infra/postgres

main → container → конкретные реализации всех зависимостей
               └→ infra/telemetry → OTel SDK / slog
```

- `cmd/trip-service/` читает конфигурацию, вызывает контейнер и управляет запуском
  и остановкой. Существующее имя команды сохранено для совместимости с ЛР1.
- `internal/container/` вручную собирает пул, репозитории, usecase, обработчики,
  логгер и телеметрию. DI-фреймворка нет.
  Здесь же создаётся аварийный логгер: `main` вызывает `container.LogError`,
  если приложение завершилось с ошибкой, в том числе до сборки контейнера.
- `internal/http/trip/{create,get,finish}/` разбирает запросы, валидирует формат,
  вызывает usecase. Общий конвертер в `internal/http/trip/convert.go`
  преобразует поездку в сгенерированный API-тип.
- `internal/http/health/` и `internal/http/ready/` содержат служебные ручки.
  У `ready` свой `contract.go` с интерфейсом проверки БД и сгенерированный мок;
  `health` не имеет зависимости от БД и не нуждается в таком интерфейсе.
  Все пять хендлеров создаются в контейнере; корневой пакет `http` связывает их
  со сгенерированным серверным интерфейсом.
- `internal/usecase/trip/{create,get,finish}/` выполняет сценарий и задаёт границу
  транзакции. Интерфейсы зависимостей неэкспортируемые, находятся в `contract.go`
  потребителя; моки генерируются рядом в `mocks_test.go`.
- `internal/domain/trip/` содержит поездку, конструктор `New`, метод `Finish`,
  ошибки и `StatusChange` — запись изменения статуса поездки в отдельном файле.
  История относится к жизненному циклу поездки, поэтому её модель находится
  в том же доменном пакете. Здесь нет HTTP, PostgreSQL и телеметрии.
  Общий пакет `model/` сейчас не нужен: параметры сценариев находятся рядом
  с usecase, а доменные типы используются напрямую.
  `New` проверяет входные данные и задаёт начальное состояние поездки;
  идентификатор и время передаёт usecase. Отдельно вызывать валидацию не нужно.
- `internal/repository/{trip,history}/` преобразует модели и выполняет SQL.
- `internal/infra/postgres/` содержит подготовку конфигурации пула, выбор исполнителя и менеджер
  транзакций; `internal/infra/telemetry/` — OTel SDK, DB tracer и `slog`.
- `internal/http/domainerror/` переводит доменные ошибки в `Problem` и записывает
  HTTP-ответы с ошибками.
- `internal/http/middleware/` содержит отдельные `Recover`, `Tracing`, `Logging`
  и `Metrics`; они явно оборачивают роутер в `internal/http/server.go`.
  Порядок входа: `Recover → Tracing → Logging → Metrics → роутер`.
  Как в [лекции про HTTP middleware](https://github.com/course-go-autumn-2026/course/blob/main/lectures-and-practice/01-http-api/lecture/lection1_HTTP_API_notes.md#4-middleware),
  логи и метрики считывают статус через собственную обёртку `ResponseWriter`.
  Используется готовый recorder из `chi`, сохраняющий дополнительные интерфейсы
  writer; общего состояния со статусом и маршрутом нет. `defer` учитывает панику
  в логах и метриках, а `Tracing` передаёт контекст спана внешнему `Recover`
  для корреляции лога паники с трейсом.
- `internal/config/` читает env через `cleanenv` и проверяет через `validator`;
  `internal/generated/` содержит результат генерации OpenAPI.

Границы импортов проверяет `depguard`. Доменная `Trip` остаётся рядом со своими
методами в `domain/trip`, без второго дублирующего типа в `model`. Для небольшого
менеджера транзакций сохранён общий пакет `infra/postgres`: он разделяет
ключ контекста с выбором исполнителя.
Технический интерфейс `executor` неэкспортируемый, объявлен в
`infra/postgres/contract.go` и объединяет операции пула и транзакции.

В п. 3 задания сборка названа частью `main`, а п. 4.1 явно выделяет `container`.
Здесь применена детальная схема из п. 4.1: `main` вызывает контейнер.
Пул создаётся вызовом `pgxpool.NewWithConfig` непосредственно в `container`,
там же проверяется `Ping` с `DATABASE_QUERY_TIMEOUT` и создаются репозитории.
`infra/postgres.NewPoolConfig` только готовит настройки пула и не открывает соединений.

## Решения

- HTTP-типам источником служит OpenAPI. Сгенерированные файлы не правятся вручную.
  `validateCreateTripRequest` разбирает JSON и проверяет данные через ozzo.
  Наличие обязательных JSON-полей проверяется отдельно от их значений, поскольку
  сгенерированные `int64` и `float64` не различают отсутствие поля и допустимый
  ноль. Неизвестные поля запрещены, в теле разрешён один JSON-объект.
- Репозитории получают пул и таймаут через конструктор. SQL собирается
  `squirrel` с параметрами `$N`. Каждый запрос ограничен таймаутом и использует
  контекст входящего запроса.
- `/ready` вызывает сервис `checkup`, который проверяет БД через `Ping`
  с `DATABASE_QUERY_TIMEOUT` и контекстом запроса. HTTP-слой преобразует результат
  в `200` или `503` со схемой `HealthResponse`.
- `TxManager.Do` открывает транзакцию и сохраняет её в контексте. Репозитории
  выбирают её из контекста, а вне `Do` используют пул. Вложенный `Do`
  переиспользует транзакцию. Успех приводит к `COMMIT`, ошибка или паника — к
  `ROLLBACK`; паника распространяется наружу. Откат имеет отдельный таймаут и
  выполняется даже при отмене исходного контекста.
- Изоляция — `READ COMMITTED`. Уникальный частичный индекс
  `trips_active_driver_uidx` запрещает две активные поездки одному водителю.
  Конфликт индекса распознаётся по `23505` и имени ограничения.
- Завершение выполняется внутри одного `Do`: `GetTripForUpdate` загружает
  поездку через `SELECT … FOR UPDATE`, usecase вызывает доменный `Trip.Finish`,
  `SaveTrip` сохраняет статус и временные отметки, затем добавляется история.
  Блокировка строки удерживается до конца транзакции. Второй конкурентный
  запрос после ожидания читает уже завершённую поездку и получает
  `ErrTripCompleted`, не меняя `finished_at`. Отсутствие поездки определяется
  при чтении и даёт `ErrTripNotFound`. Чтение с блокировкой вне `Do` запрещено.
  `UPDATE … RETURNING` возвращает значения с точностью PostgreSQL: именно они
  используются в HTTP-ответе и истории. По сравнению с ЛР1 успешное завершение
  делает дополнительный `SELECT`; HTTP-контракт и бизнес-правила сохраняются.
- Создание и завершение вызывают запись поездки и истории внутри одного `Do`.
  История дополняется новой записью на каждый переход: `NULL → active`, затем
  `active → completed`. Ошибка записи истории откатывает изменение поездки.
- По сигналу HTTP-сервер перестаёт принимать запросы, дожидается текущих, затем
  OTel SDK сбрасывает накопленные сигналы, затем закрывается пул БД.
  Всё ограничено общим `SHUTDOWN_TIMEOUT`; при истечении бюджета HTTP-соединения
  принудительно закрываются.

## Телеметрия и проверка

Логи — JSON в stdout с уровнем из `LOG_LEVEL`. Внутри запроса `trace_id` и
`span_id` добавляет обработчик `slog` из контекста. Access-log `request handled`
пишется один раз после обработки: шаблон маршрута, метод, статус, длительность.
Для 2xx/4xx используется Info, для 5xx — Error. Бизнес-события `trip created`
и `trip completed` содержат `trip_id` и пишутся после успешного коммита.
Тела запросов и ответов, SQL-параметры в телеметрию не попадают.

`otelhttp` принимает W3C `traceparent`; имя спана — `METHOD /route/{parameter}`.
Обёртка над `otelpgx` установлена на пул и создаёт спаны SQL-запросов с
`db.operation.name` и `db.collection.name`. Ошибки отмечены `codes.Error` и
`error.type`. `BEGIN`/`COMMIT`/`ROLLBACK` не относятся к отдельной таблице,
поэтому у них пустой `db.collection.name`.

HTTP- и DB-гистограммы записываются явно с нужными лейблами и границами
в секундах; встроенные метрики инструментаторов отключены, чтобы не
дублировать серии с другим набором лейблов. Имена OTel:

- `http.server.request.duration`, `http.server.active_requests`;
- `db.client.operation.duration`;
- `tripgo.trips.created`, `tripgo.trips.completed`, `tripgo.trips.active`.

Бизнес-счётчики увеличиваются только после коммита. Gauge активных поездок
считает текущее состояние БД при сборе, поэтому корректен после перезапуска.
Collector не участвует в `/ready`: его недоступность не блокирует API.
Экспорт асинхронный, очередь ограничена SDK; при долгом отказе часть телеметрии
может быть потеряна. Ошибки экспорта тоже идут в JSON-лог на уровне `Warn`.

1. Выполните запросы из примера выше. Возьмите `trace_id` из `request handled`
   и откройте `<Jaeger URL из connect>/trace/<trace_id>`. Внутри HTTP-спана должны
   быть SQL-спаны поездки и истории.
2. В Grafana импортируйте [готовый дашборд](config/grafana-trip-service.json),
   источник данных — `prometheus` из окружения курса. Имена метрик после
   преобразования Collector: `http_server_request_duration_seconds_bucket`,
   `db_client_operation_duration_seconds_bucket`, `tripgo_trips_created_total`
   и `tripgo_trips_completed_total`.
3. Сделайте скриншоты трейса и дашборда для PR. Они должны показывать реальные
